Technical Requirements Document

Implementation architecture, data model, APIs, analytics and quality controls

TRD  •  Version 1.0  •  19 October 2026

1. Technical overview

The architecture should remain intentionally simple and modular. Recommended MVP stack: React + TypeScript for the frontend, FastAPI for the Python backend, PostgreSQL for relational storage, pandas for controlled data preparation/analysis, and SQL for aggregations and reporting. This is a proposed stack, not a claim that an existing repository already uses it.

5. Data and calculation rules

Use DECIMAL/NUMERIC for currency and explicit currency/rounding conventions; do not use binary floating point as the database currency type.

Store timestamps consistently (UTC internally where timestamps are used) and define the reporting timezone for date boundaries.

Validate unique primary IDs, foreign-key integrity, non-negative amounts where appropriate, valid dates and allowed status values.

Normalize annual income to monthly income only where assumptions are documented; DTI requires gross monthly income and monthly debt obligations on a consistent basis.

Compute overdue amount from unpaid amounts whose due dates are before or on the reporting cutoff, using the agreed partial-payment allocation rule.

Define default status and observation window explicitly; delinquency or one missed payment should not automatically be treated as default unless the chosen policy says so.

Keep SQL aggregations and Python metric definitions consistent; test both against known fixtures.

Do not treat missing data as zero. Return a missing/unknown state or exclude it according to a documented metric policy.

6. Risk rules engine

Implement the MVP as a deterministic service. Inputs should be a validated feature object; outputs should include risk_band, reason_codes, human-readable explanation, rule_set_version and missing_inputs. Keep thresholds in configuration or database records and validate that bands do not overlap unintentionally.

Illustrative pseudocode

def assess_risk(features, rules):    if features.has_critical_missing_inputs:        return Assessment(            band="Review Required",            reasons=["Required income/score/repayment data missing"],            rule_version=rules.version,        )    reasons = []    score = 0    if features.dti_pct >= rules.high_dti_pct:        score += rules.high_dti_weight        reasons.append("High debt-to-income ratio")    if features.credit_score < rules.low_score_threshold:        score += rules.low_score_weight        reasons.append("Credit score below configured threshold")    if features.overdue_days >= rules.overdue_days_threshold:        score += rules.overdue_weight        reasons.append("Repayment overdue")    band = rules.map_score_to_band(score)    return Assessment(band=band, reasons=reasons, rule_version=rules.version)

The scoring weights and thresholds above are placeholders. They must be calibrated to the project’s chosen policy and test dataset before use.

8. Query and analytics expectations

Use parameterized SQL for all dynamic values; allowlist sort columns and directions.

Use GROUP BY for segment summaries, CASE for explicit band mapping when appropriate, JOINs for borrower/loan/repayment linkage, and window functions for ranking or cumulative trends.

Apply pagination at the database/API layer rather than downloading the full table to the browser.

Create indexes for commonly searched IDs, borrower name where supported, loan issue date, status, borrower foreign keys and repayment due/payment dates.

Vintage queries must align cohort start dates, observation cutoffs and loan age. Do not compare cohorts at unequal ages without a clear label.

Add query plans and indexes only after observing realistic query patterns; avoid premature complexity.

9. Frontend implementation rules

Use a shared app shell: fixed or collapsible sidebar, compact top bar, page title, date range and profile menu.

Build reusable KPI cards, filter bars, data tables, risk badges, empty states, chart containers and explanation panels.

Use one spacing scale and design tokens for canvas, surfaces, typography, borders, radii and semantic status colours.

Keep the dashboard to four main KPIs and a small number of charts; use dedicated pages for deep analysis.

Show chart tooltips, axis labels, readable legends and text summaries. Do not rely on colour alone.

Synchronize URL/query state for shareable filters where practical; ensure reset and pagination behavior are predictable.

Use skeleton/loading states and user-readable errors; never show stale data as fresh without a timestamp.

10. Security and privacy

Enforce authentication and authorization on the server, not only by hiding frontend controls.

Validate all request parameters and imported files; cap upload size and reject unexpected file formats.

Store secrets in environment/secret management; commit only .env.example with dummy values.

Use least-privilege database credentials and parameterized queries.

Mask or minimize personal data in logs; protect exported files and define retention expectations.

Use synthetic or de-identified demo data and avoid publishing real borrower records in screenshots or repositories.

Log sensitive administrative changes and access-relevant events without logging secrets or unnecessary personal information.

12. Deployment and environment

Maintain separate development and production configuration.

Provide database migrations and a repeatable seed dataset for local development.

Use health/readiness checks for API and database connectivity.

Configure structured logs, error reporting and basic service monitoring.

Run tests and dependency/security checks before deployment.

Document local setup, environment variables, migration, seed, test and build commands in README.

13. Technical acceptance criteria

Every endpoint validates inputs and returns documented response schemas.

Every metric has a tested formula and explicit reporting cutoff.

Risk assessment is deterministic for a given input and rule version.

Data imports produce a quality summary and never silently discard rejected rows.

Large tables use server-side pagination and safe query parameters.

Core screens provide responsive, accessible loading/error/empty states.

An end-to-end test can ingest a sample dataset and produce a reconciled portfolio report.
